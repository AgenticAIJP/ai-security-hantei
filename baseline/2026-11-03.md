## AIS-20261103-02　Cursor マーケットプレイスの偽「Claude Code」拡張（root: 6ae8bb0cf27e65e1fc09d022）

### 1. 判定カード
- 初報：2026/10/29（Cursor の発表。2026/10/30 11:30 PT に IOC の更新と対象版の明確化）。速報は「初報」としており、一次発表の日付と合う。
- 一次出典：https://cursor.com/blog/claude-code-extension-security-notice
- 何が起きたか（確認済み）：Cursor の VS Code 拡張マーケットプレイスで、Anthropic.claude-code の 2.1.312 と 2.1.313（Windows・macOS）が改ざんされた版として、10/29 の約 2:27am PT から約 1:35pm PT まで配布された。Anthropic が作った版ではない。端末情報を送り、攻撃者の SSH 公開鍵を追加し、逆向きの SSH トンネルを張って永続化を試みる。
- AI の関与：AI が攻撃を行った証拠は発表にない。標的は AI コーディング拡張で、AI 開発環境が供給網の入口になった事案。攻撃への AI 利用は不明。
- 深刻度：高。開発者端末は認証情報・ソースコードに近い。ただし Cursor は、多くの端末では SSH サービスの有効化に管理者権限が要るため遠隔ログインは失敗するとし、攻撃者のサーバーも停止済みと書いている。
- 影響を受ける人：両方（主に開発者を抱える企業と個人開発者）。
- 今すぐできること：企業＝該当期間の導入・更新の有無を拡張機能の管理情報で洗う、該当端末で SSH 認可鍵の確認。個人＝Cursor の確認手順で `svc-telemetry` の鍵の有無を調べる、見つかれば隔離して認証情報を変更。
- 確度：高（発表自体は一次）。未確認：影響人数（速報の「最大 5,000 人」は、今回開いた Cursor ブログ本文では見つけられず、X 投稿由来と思われる＝未確認）、侵入経路（なぜ改ざん版が登録できたか）は発表で説明されていない。

### 2. 技術分析
- 原因の型：拡張機能の配布基盤（マーケットプレイス）への不正な版の混入。正規の公開元名を装った供給網攻撃。Cursor は鍵の更新と基盤の再構築を実施したと書くが、混入の経路は書いていない。
- 平時の備え：拡張機能の許可リスト化と版の固定、自動更新の抑止（特に AI エージェント機能を持つ拡張）、導入拡張の棚卸しと端末管理での配布管理、SSH の認可鍵・常駐タスクの変更監視、開発端末から社内資源への権限分離。
- 自社で確かめる手順：(1) 該当期間に更新された拡張の一覧、(2) 全開発端末の `authorized_keys` と起動時タスクの差分、(3) 発表の IOC（IP・ファイル・計画タスク）を EDR／ログで照合、(4) 見つかれば端末を隔離し、端末から使えた認証情報を信頼できる別端末から変更。拡張を消すだけでは不十分と Cursor が明記している。

### 3. 前提への問い
- 「多くの端末では失敗する」は Cursor 自身の説明。端末情報（ユーザー名・環境変数名・Git のメールなど）の送信は成功しうる、と発表も書いている。失敗＝無害とは言えない。
- 約 11 時間という配布時間は、ダウンロード数ではない。実際の導入数は公式本文では確認できない。
- 供給網の根本原因が未説明のため、「基盤を再構築した」で再発リスクが下がったかは外から確かめられない。

### 4. 中小企業向け
- 対策：AI コーディングツールを使う社員の端末を把握する／拡張機能は会社が承認したものだけにする／自動更新を一定期間遅らせる／端末の SSH 設定を平時に記録する。
- 問い合わせ文（提供元へ）：「貴社マーケットプレイスで、◯月◯日の期間に当社の端末へ導入・更新された拡張の版の一覧と、該当版の検出方法を教えてください。」

### 5. 個人向け
- Cursor で Claude Code 拡張を 10/29 に入れた・更新した人は、発表の確認コマンドで鍵の有無を調べる。見つかれば Cursor の削除スクリプトと、パスワード・トークンの変更。見つからなければ追加の作業は不要と発表は書いている。
- 拡張機能は公開元名が同じでも版と入手元を確かめる。

### 6. 再発防止の制度
- マーケットプレイス運営者に、拡張の署名検証・公開時の二段階承認・公開元名の保護と、事案時の影響範囲（導入数・版）の公表を求める枠組み。AI エージェントが入る拡張は、権限の宣言と審査を厚くする。

### 7. 攻め手の型と先回りの守り
- 型：信頼された名前を使った拡張の差し替え → 開発者端末への足場。守り：配布経路の署名検証、拡張の権限最小化、端末側の常駐物検知。手順は書かない。

### 着眼点のリスト
1. 公開元名を装った供給網攻撃（正規名が信頼の根拠にならない）
2. AI 開発環境が攻撃面になった
3. 失敗しうるが情報は送られる（部分成功）
4. 拡張の削除だけでは残る永続化
5. 端末から使える認証情報の変更が本題
6. 約 11 時間の窓と対象版・OS の限定
7. 侵入経路の未説明
8. 影響人数が一次で確認できていない

## AIS-20261103-04　Cloudflare Workers AI の GLM-5.3 で他の顧客データが混入（root: 6ae8a7b5f27e65e1fc09c734）

### 1. 判定カード
- 初報：2026/10/26（Cloudflare ブログ。SGLang 側の投稿と同時の協調開示）。速報は「初報」としており、合う。事象の期間は 2026/8/27〜9/9。
- 一次出典：https://blog.cloudflare.com/kv-cache-exposure-remediation/
- 何が起きたか（確認済み）：GLM-5.3 を 8/27 から 9/9 の間に使った少数の顧客の応答のうち 155 件に、直前に同じモデルへ送られた他の顧客のリクエストのデータが含まれた。対象は 681,280 トークンより長いプロンプトへの応答。9/8 に研究者から報告があり、9/9 にモデルを停止して修正、同日再開。
- AI の関与：確認済み（AI 推論基盤そのものの不具合。攻撃にAIが使われたのではない）。根拠＝AI モデルを動かす推論エンジンの KV キャッシュの扱いの不具合。
- 深刻度：中。件数は 155 件と少なく悪用の証拠もないが、他の顧客のプロンプトや生成内容が見えうる点でテナント分離の失敗であり、同種の推論エンジンを使う他社にも当てはまる。
- 影響を受ける人：企業が中心。
- 今すぐできること：企業＝提供元に通知有無を確認／超長文入力に機密を入れない運用／自社で推論エンジンを使うなら SGLang v0.5.22 以降。個人＝影響を受けた顧客には Cloudflare が個別に知らせるかは本文からは読み切れず、個人の対応は特にない。
- 確度：高（一次）。未確認：影響を受けた顧客数、通知の方法・範囲（ブログ本文から読み切れていない）。

### 2. 技術分析
- 原因の型：二つが重なった。(1) 設定の不一致：コンテキスト長 1,048,576 トークンに対し、prefill GPU の KV プールが 681,280 トークン分しかなかった（Cloudflare は発表前から不一致を認識。エンジンが長すぎる要求をエラーにすると期待していた）。(2) SGLang の不具合：分離構成（prefill／decode）で、拒否された要求がエラーにならず、プレースホルダーの KV だけが転送され、decode 側が前の要求のページを読んだ。
- 平時の備え：KV プール容量とコンテキスト長の一致を起動後のエンジンから直接検査する。応答コードだけでなく出力の中身で試験する（Cloudflare が自ら「HTTP の成否と性能しか見ていなかった」と書いている）。拒否経路のエラー処理の試験。
- 自社で確かめる手順：自社で推論エンジンを運用している場合、(1) 設定された最大文脈長と実際のプール容量の比較、(2) 長大入力の試験で他の要求の内容が混ざらないか目印文字列で確認、(3) エンジンの版の確認。

### 3. 前提への問い
- 「意図的な悪用の証拠なし」は、Cloudflare のログ分析（研究者と自社試験を除き、タイミングと量が通常利用と一致）に基づく。ただし、混入した側の内容が何だったかは公表されていない。
- 影響が「155 件」で閉じるかは、同社が確認できたリクエスト記録の範囲に依存する。
- 同社は 8/27 の開始時点から不一致を認識していた。発表は「想定外のエンジンの挙動」と説明しているが、組織としての検証の穴でもある。
- 同種の不具合は SGLang の課題として 7/6 に別の利用者から報告されていた（ブログに記載）。

### 4. 中小企業向け
- 対策：AI の推論サービスに機密を送る前に、提供元のテナント分離の説明と過去の事故対応を確認する／長大なプロンプトに個人情報・契約書を丸ごと入れない／ログ・保存設定を確認する。
- 問い合わせ文（提供元へ）：「◯月◯日〜◯月◯日に当社アカウントのリクエストが他の顧客の応答に含まれた、または他の顧客のデータが当社の応答に含まれた可能性があるか、調査結果と根拠を教えてください。」

### 5. 個人向け
- AI サービスに入れた長文は、他の人に見えうるという前提で、住所・口座・認証情報は入れない。サービス側から通知が来たら案内に従い、記載の認証情報があれば変更する。

### 6. 再発防止の制度
- AI 推論基盤について、テナント分離の失敗の報告・公表の基準、第三者による分離の検証、OSS 推論エンジンの脆弱性の協調開示の標準化。報告から公表まで 7 週間かかった点について、利用者への通知時期の基準。

### 7. 攻め手の型と先回りの守り
- 型：共有 GPU メモリ上の他の利用者のデータを引き出そうとする、超長文入力による分離の試し。守り：ページの所有権管理、使用後の消去、拒否経路の統一処理、異常応答の監視。具体的な再現手順は書かない。

### 着眼点のリスト
1. 推論基盤（共有メモリ）でのテナント分離の失敗
2. 設定の不一致を知りながら出荷し、HTTP の成否しか見ていなかった
3. OSS 推論エンジンの不具合が顧客データの混入に直結
4. 155 件・長大プロンプトだけという限定
5. 研究者の報告から 1 日で修正、公表まで約 7 週間
6. 悪用の証拠なしの根拠の範囲
7. 他の SGLang 利用者への波及（v0.5.22 以降への更新）
8. 利用者への通知の有無が本文から読み切れない

## AIS-20261103-03　ユミルリンク「Cuenote FC」不正アクセスとりそな 3 行（root: 6ae86804f27e65e1fc09a718）

### 1. 判定カード
- 初報：ユミルリンク第一報＝2026/10/19、第二報＝2026/10/26。りそな銀行など 3 行の発表は 10/27（速報は「初報（10/27）」と書くが、この事案全体の初報は 10/19。3 行の発表は委託先の事案を受けた各社の発表）。

- 何が起きたか（確認済み、ユミルリンク第二報）：10/16 に不正アクセスを確認。ライブラリの脆弱性を突かれ、サポート・品質管理担当者の認証情報を取得され、不正プログラムの設置とデータベースからのデータ出力、他システムへのログイン試行があった。Cuenote FC で 49 システムが情報漏えいで、延べ 51,628,280 件（調査中が 16 システムあり増える可能性）。第一報では 5 システム・延べ約 900 万件の試算だった。
- AI の関与：関与の記載なし（不明に近い。ライブラリの脆弱性が原因）。
- 深刻度：高。件数の大きさ、委託先経由で多数の企業の顧客に及ぶこと、すでに当該ドメインを使ったなりすましメール（カード会社名での「ご利用確認のお願い」）が確認されている。
- 影響を受ける人：両方。
- 今すぐできること：企業＝Cuenote FC 利用の有無と、個別連絡の有無の確認、自社顧客へのなりすまし注意の周知、委託先の管理画面・API の接続元制限と認証情報の見直し。個人＝メール・SMS のリンクを開かない、同じパスワードの使い回しを変更。
- 確度：高（一次は読めた）。未確認：3 行の発表内容と各社の影響件数（ユミルリンクが調査中）、脆弱性のあるライブラリの名称（公表されていない）。

### 2. 技術分析
- 原因の型：委託先 SaaS のライブラリ脆弱性 → 特権的な社内アカウントの認証情報の窃取 → 他システムへの横展開（同じ担当者の認証情報とセッション情報の悪用）。操作画面・API に接続元 IP 制限がなかった環境があった（同社の再発防止策に記載）。
- 平時の備え：委託先のサポート用アカウントの権限分離と接続元制限、ライブラリの更新管理、不正プログラム設置の常時監視、顧客データの最小保持。
- 自社で確かめる手順：(1) 委託先を使うメール配信・フォームの一覧、(2) 保管される項目（メール、氏名、生年月日など）の洗い出し、(3) 委託先からの連絡窓口の確認、(4) 自社ドメインを装うメールの監視（DMARC など）。

### 3. 前提への問い

- 件数が第一報から約 5.7 倍（約 900 万→約 5,163 万）に増えた。今後さらに増える可能性があり、「現時点」の数字として扱う。
- 「悪用の事実は確認されていない」と、なりすましメールの確認は併存している。

### 4. 中小企業向け

- 問い合わせ文（委託先へ）：「当社の配信システムは今回の不正アクセスの対象か。対象なら流出した項目・件数・期間と、当社が個人情報保護委員会へ報告する際に必要な情報をいつ提供できるか。」

### 5. 個人向け
- 銀行やカード会社を名乗るメール・SMS は、リンクを開かず公式アプリや公式サイトから確認する。パスワードの使い回しを改める。メールアドレスだけでも標的型の文面に使われうる。

### 6. 再発防止の制度

### 7. 攻め手の型と先回りの守り
- 型：委託先の特権アカウントを足がかりに、多数の顧客データへ横展開。漏えいしたアドレスを使った、正規の事業者を装うフィッシング。守り：接続元制限、認証情報の分離、顧客への事前の注意喚起。手順は書かない。
