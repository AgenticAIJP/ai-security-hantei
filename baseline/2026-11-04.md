### 2. 技術分析
- 原因の型：(1) 初期侵入の経路は公表されていない。(2) メール送信 API の資格情報の漏えいと、総当たりによるパスワード突破（認証の弱さ）。(3) 緩和後の再悪用（URL パースの混乱を突く脆弱性）。封じ込めの不完全さが二度目の不正メールにつながった。
- 平時の備え：API 資格情報の定期変更と最小権限、送信量・宛先の上限と異常検知、ログインと API の多要素・IP 制限、ログイン試行の制限、入力 URL の検証の設計と診断、外部機関による定期診断、侵害後に「連携を止めたら終わり」としない再点検。
- 自社で確かめる手順：(1) 自社が使うメール送信 API の資格情報の棚卸しと変更、(2) 送信ログで想定外の宛先・量がないか、(3) 外部連携の許可元と権限の見直し、(4) 登録者向けの連絡文面の準備、(5) SPF・DKIM・DMARC の設定確認。

### 3. 前提への問い
- 「推定値」の件数は上限か下限か：発表は「最大」の意味合いで書いているが、調査継続中で確定していない。
- 「侵入経路を遮断した」（第 2・9 報）後に再び不正メールが出ている：遮断の宣言だけでは安全の根拠にならない。
- フィッシングメールの 869,575 通が自社保有外宛て：どこから宛先を得たのか（別の漏えい元か）は未説明。
- 警察への調書提出は、被害の拡大や攻撃者の特定とは別の話で、深刻度を下げる材料にも上げる材料にもならない。

### 4. 中小企業・自治体向け
- 対策：契約サービスの発表を毎日確認する担当を置く／メール送信 API などの認証情報を直ちに変更／2 段階認証を全管理者に設定／登録者へ「この件に便乗した偽の連絡に注意」と一斉に周知／重要連絡は別経路（電話・窓口）でも確認できるようにする。
- 問い合わせ文（提供元へ）：「貴社の第 25 報にある、当団体のアカウントに関する影響の有無、漏えいした可能性のある項目と件数、API 認証情報の変更要否、再発防止の時期を、書面でご回答ください。」

### 5. 個人向け
- 防災・自治体・学校の連絡サービスから来たように見えるメールや SMS でも、リンクは押さず、公式サイトや公式アプリから確認する。
- 氏名・住所・パスワード・口座情報は、メールの案内から入力しない。
- 同じパスワードを他で使っていれば変更する。不審なメールは、契約元の窓口に知らせる。

### 6. 再発防止の制度
- 防災・自治体向けの連絡基盤の事業者に、重要インフラに準じた監査と事案時の公表手順（件数の更新ルール、封じ込めの確認）を求める。
- 自治体の調達で、2 段階認証・API の認証管理・外部診断の実施を条件にする。
- 複数サービスをまたぐ事案での関係機関への報告を一本化する枠組み（個人情報保護委員会、総務省、経済産業省など）。

### 7. 攻め手の型と先回りの守り
- 型：資格情報の窃取 → 総当たり → 送信機能の悪用による大量のフィッシング。守り：資格情報の最小権限と短い有効期間、送信の上限と異常検知、2 段階認証。手順は書かない。
