### 1. 判定カード
- 初報：2026/10/16（10/18 に案内ポータルを公開。最新の更新は 2026/11/04 05:01）。Room では初掲。
- 一次出典：https://studio.design/ja/whats-new/unauthorized-access-2026-10 ／ https://studio.design/ja/security/notice/2026-10-incident （両方を開封）

### 2. 技術分析
- 原因の型：公開機能の脆弱性の悪用によるクラウド環境への侵入。発見まで約 2 週間（9/30〜10/1 → 10/13）。暗号化していても復号の鍵が同じ環境から読めたため、暗号化が実質効かなかった点が特徴。
- どこで止められたか：①脆弱性の事前の発見と修正。②暗号化鍵とデータの分離（鍵管理専用の仕組み、環境の分離）。③外部サービスの認証情報を保管しない設計、または短期の権限だけを使う設計。④アクセスの異常（環境内の大量読み出し）の早期検知。⑤不要なデータ（アーカイブ、ゴミ箱の回答）の削除。
- 平時の備え：鍵と暗号化データの別管理、保存データの保管期間、ゴミ箱の本当の削除、フォームの回答の保存期間の設定、機密のキーの定期更新。
- AI 時代の守りと検知（推定）：公開機能の弱点が AI の補助で見つかりやすくなる前提で、自社の機能を自社で先に検査する頻度を上げる。ログ異常の検知に AI を使い、人が停止を決める。確かめる人：セキュリティ担当と、契約した専門会社。AI を使う危険：機密の入力、誤検知、AI ツールの改ざん。効果の見込みは推定。
- 自社で確かめる手順（自社と許可を得た範囲）：(1) Studio など外部サービスに登録した API キーとトークンの一覧、(2) それぞれの発行元で再発行と失効ができるか、(3) フォームで集めた個人情報の保存場所と期間、(4) パスワードの使い回し、(5) 公開前のプレビュー URL の有無。

### 3. 前提への問い
- 「取得された事実は確認できていない」は、取得されなかったことの証明ではない（会社も取得されたとみなして対応している）。
- 「暗号化していた」は、鍵が同じ環境から読めたなら、実質の保護になっていなかったのでは。
- 「書き換えの記録なし」は、取得された権限に書き換え権限があった以上、記録の範囲と調査の確かさがどこまでかが問い。
- 「二次被害は調査中」のまま、顧客に API キーの失効を任せる構図は、顧客側の作業が完了するまでの空白期間が長い。
- 確認が 10/13 と、侵入（9/30〜10/1）から約 2 週間後。

### 4. 中小企業向け
- 同じ原因が自社にもあるか：自社が Studio で作ったサイトにフォームがあるか。Studio に API キー、reCAPTCHA、Webhook、Google スプレッドシート連携、パスワード保護ページを登録したか。あるなら対象。

### 5. 個人向けの手引き
- 漏れた情報：Studio の登録者はアカウント情報など。Studio 製サイトのフォームに送信した人は、フォームの回答（氏名、連絡先、問い合わせ内容など、サイトによる）。
